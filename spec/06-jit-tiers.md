# Tiers 1 and 2: the JIT

## 6.1 Tier 1 is a build step, not a compiler

The baseline JIT does not do instruction selection or register allocation. At build time we compile every opcode's fast paths into an object file and extract the unrelocated machine code plus its relocation records, producing a library of stencils. At runtime, compiling a function is walking its bytecode, memcpying the right stencil for each opcode into a code buffer, and patching in the constants, register offsets and branch targets.

Xu and Kjolstad measured code generation two orders of magnitude faster than LLVM at `-O0` producing code that ran 14% faster than LLVM `-O0` output, and their Wasm baseline compiler beat Chrome's Liftoff by 4.9x to 6.5x on compile speed. Cognica's production SQL engine reports 50 to 200x faster compilation than LLVM. Deegen's generated baseline JIT has, in their words, negligible compilation cost, and its output runs 4.60x faster than PUC Lua's interpreter.

For us that means tier up can happen at eight invocations, the same as V8's Ignition to Sparkplug threshold, because compiling is cheaper than running the function twice more in the interpreter.

## 6.2 The thing that will go wrong, and the plan for it

Haoran Xu's own writeup on copy and patch is blunt about the failure mode: naive stencils produce poor code, because if each stencil is a self contained function then every operation becomes a call and the overhead swamps the win, unless you restructure the handlers into continuation passing style so that stencils fall through into each other.

That restructuring is the actual engineering, and it is harder for JavaScript than for Lua because more of our operations are polymorphic. `o.x` is not one operation, it is a cache probe plus a shape guard plus a load, with four or five shapes of fast path and a runtime call behind them.

The plan:

**Handlers are written in continuation passing form in the DSL** from document 05.2, so the generated stencils end with a fall through or a tail jump rather than a return.

**Hot and cold splitting.** The fast paths go in the main code buffer in bytecode order. Slow paths and runtime calls are emitted out of line in a cold region, so the hot instruction stream stays dense. Deegen does this automatically and reports it as one of the meaningful wins.

**Inline caches get inline slabs.** A property access site reserves a small patchable region in the generated code, and the first time it executes, the runtime writes a monomorphic check and load directly into that region. This is self modifying code, it needs the W^X discipline from 6.7, and it is what makes baseline JIT property access competitive rather than a call into a cache lookup helper.

**Register pinning.** The interpreter's frame pointer, the isolate pointer and the tag constants live in fixed machine registers across all stencils, established by the calling convention the stencils are compiled with. Deegen lists register pinning and tag register optimization as automatic optimizations, and they matter a lot.

**The measurement gate.** Document 13 puts a copy and patch spike in M2 whose exit criterion is a measured speedup over the interpreter on property heavy code, not just on arithmetic. If polymorphic property access in stencils does not beat the interpreter by a worthwhile factor, we find out before the architecture depends on it. This is open question one in document 17.

## 6.3 Building the stencils

The stencil library is produced at build time by compiling the generated handler code with a C toolchain at `-O2` for each target, then parsing the object file for code and relocations. That is how the technique works and there is no way around the toolchain dependency.

Practical consequences we have to design for rather than discover:

We need stencils for four target pairs: x86-64 and aarch64, on Linux and macOS. Cross compilation is required so that CI does not need four machines, and the stencil extraction has to be deterministic so the build is reproducible.

We ship pre-generated stencils in the published crate. A user running `cargo install katsu` must not need clang. The stencils are build artifacts checked into the release, regenerated by a maintainer command, with a CI job that regenerates them and fails if the output differs from what is committed.

Stencil extraction is a chunk of code that understands ELF and Mach-O relocation types. That is a bounded, testable, unglamorous piece of work and it is on the critical path, so it gets its own milestone slot rather than being assumed.

## 6.4 Tier 2: the optimizing compiler

A CFG based SSA IR, not sea of nodes. V8 spent three years migrating TurboFan off sea of nodes onto Turboshaft and reported compile time roughly halved with code quality equal or better, citing debuggability and unpredictable scheduling as the reasons. Maglev, their mid tier, deliberately chose CFG SSA over what they call TurboFan's "more flexible but cache unfriendly" representation. We start where they finished.

The pipeline:

1. **Graph building** from bytecode plus the feedback vector. Feedback turns `Add` into a typed int32 add with a guard, and `GetProp` into a shape guard plus a fixed offset load.
2. **Inlining**, driven by call site feedback, with a size budget and a depth limit.
3. **Typed lowering**, turning generic operations into typed ones wherever a guard establishes the type.
4. **Redundancy elimination**: common subexpressions, redundant guards, redundant shape checks, load elimination through an alias analysis that understands our object model.
5. **Escape analysis and scalar replacement.** This is where a large share of real JavaScript speedups live, because idiomatic code allocates short lived objects constantly.
6. **Loop optimizations**: invariant hoisting, bounds check elimination where a guard on the array length dominates.
7. **Lowering to machine level**, register allocation, and emission.

Effects are explicit in the IR. Every operation that can throw, allocate, call, or read and write the heap carries its effect, and the scheduler may not reorder across effects it does not understand. This is the boring discipline that keeps an optimizing compiler correct, and it is precisely what the sea of nodes design makes hard to reason about.

## 6.5 Speculation and deoptimization

Speculation is the whole point of a JavaScript JIT. The feedback says this site only ever saw int32, so we compile an int32 add, and we install a guard that bails out if that ever stops being true.

The discipline comes from the formal work on this: "Correctness of speculative optimizations with dynamic deoptimization" (POPL 2018) and "Formally verified speculation and deoptimization in a JIT compiler" (POPL 2021) both model an IR where deoptimization sync points and the assumptions being made are explicit IR constructs. We take that shape, because the alternative is an optimizer that can silently invalidate an assumption three passes after it was made.

So each guard in our IR carries a **frame state**: the bytecode offset to resume at, and a description of where every interpreter register's value currently lives, which may be a machine register, a stack slot, a constant, or a recipe for materializing an object that escape analysis deleted.

Deoptimizing means reading that frame state, materializing anything escape analysis removed, writing an interpreter frame onto our own stack, and jumping into the interpreter at the recorded offset. Because the stack is ours (document 5.4) this is mechanical rather than terrifying.

**Deopt loops are the failure mode to design against.** A function that deoptimizes, recompiles with the same wrong assumption, and deoptimizes again will burn the process. Each speculation records why it failed on the function's blueprint, recompilation is forbidden from making a recorded failed assumption again, and a function that has deoptimized more than a threshold gets pinned at tier 1 permanently.

## 6.6 On stack replacement

A function containing a hot loop may never be re-entered, so waiting for the next call to tier it up is waiting forever. The loop back edge counter triggers OSR: compile the function, then transfer the currently executing interpreter frame into the compiled frame mid loop.

OSR entry is compiled as a separate entry point with its own frame state mapping, going the opposite direction from a deopt: read interpreter registers, write machine registers and stack slots, jump to the loop header. Deegen generates OSR entry automatically for its baseline JIT, which is a good sign that the mechanism is tractable when the frame layout is known.

We support OSR into tier 1 and tier 2. OSR into tier 1 matters more than it sounds, because a script that is one big loop at the top level is a common shape and it never gets a second call.

## 6.7 The backend decision, deliberately deferred

Two candidates for tier 2's machine code emission.

**Cranelift.** Pure Rust, no LLVM dependency, designed for compile speed, hardened by Wasmtime, and it has user stack maps where the producer declares which values are live at a safepoint and attaches entries via `declare_needs_stack_map` and `append_user_stack_map_entry`. Safepoint spills and reloads are ordinary IR loads and stores, so the optimizer can see them. That is the right foundation for deopt frame states.

What I could not find is any Cranelift support for deoptimization itself: tiering down, deopt points, frame reconstruction. The absence of results is itself informative, and it means we would be building deopt on top of stack maps ourselves.

**Our own backend.** Direct machine code emission for x86-64 and aarch64, either hand rolled or over `dynasm-rs`, with our own linear scan register allocator. Full control over deopt, calling conventions and patchable sites. Considerably more work, considerably more `unsafe`, and it is exactly the code that produces memory corruption CVEs in other engines.

The decision is made by prototype at M6, not by argument here. The IR is designed with a backend trait so that both are implementable, and document 17 makes this open question two. If Cranelift works, we save months. If it does not, we know before the IR is set in stone.

## 6.8 Code memory is a budget, not a resource

Under document 02's memory goal, compiled code cannot be immortal. A long lived process that touched fifty thousand functions once must not carry fifty thousand compiled bodies.

So: tier 1 and tier 2 code buffers are allocated from a code region with a budget, tracked per isolate. When the budget is exceeded, the least recently executed compiled code is discarded and the function reverts to its next lower tier. Discarding requires knowing no frame is currently executing that code, which the stack walk already tells us.

This is unusual. Most engines treat compiled code as permanent. It is the direct consequence of taking a 10x memory target seriously, and it also gives us something the others do not have, which is a hard ceiling on code memory for embedded and serverless deployments.

## 6.9 Writing executable memory safely

Every platform has its own rules and getting them wrong is a segfault or a security hole.

On Apple Silicon, MAP_JIT pages enforce W^X per thread. The correct sequence is `pthread_jit_write_protect_np(false)`, write, `pthread_jit_write_protect_np(true)`, then `sys_icache_invalidate`. Use the pthread call rather than `mprotect`: CPython measured a 1.4% overall interpreter speedup from that one change. The classic bug is leaking write mode on an early return or a panic, which leaves the thread unable to execute its own code, so **the toggle is an RAII guard type that cannot be leaked and cannot be constructed twice on the same thread**. Newer code should prefer `pthread_jit_write_with_callback_np`, which only permits callbacks registered through `PTHREAD_JIT_WRITE_ALLOW_CALLBACKS_NP`, because attacks exist that induce unintended calls to the plain toggle through `dlsym`. We also need the JIT entitlement under the Hardened Runtime, which affects how we sign and distribute macOS builds.

On Linux, dual mapping: one writable mapping and one executable mapping of the same pages, with the writable one never handed to anything but the assembler.

Apple's own guidance is that giving one thread write access while another has execute access on the same region is an attack vector, which is another reason the thread per core isolate model in document 03.6 is the right shape: one thread owns an isolate's code region and nobody else touches it.

## 6.10 What tier 2 is expected to achieve

Document 02.6 sets the trajectory: roughly half of V8 on compute benchmarks when tier 2 first works, parity within noise at 1.0, and beating V8 at all being a genuine achievement rather than a baseline expectation.

The comparison point worth holding onto is that Deegen's automatically generated baseline JIT, with no optimizing tier at all, landed 33% behind LuaJIT's full optimizing JIT on average and ahead of it on 13 of 44 benchmarks. Generated tiers are not a compromise for the code quality they produce, they are a compromise for the code quality per engineer-year they produce, and that is the constraint this project actually has.
